# 法规库更新流程（上线后）

> 2026-10-21 定稿。法规库已**封版**（快照 `final-sealed-20261021.tgz`），
> 之后每次加法规/改法规都算「拆封」，必须按本流程走完并留痕。

## 0. 三条铁律

1. **没点名的文件一律不碰** —— 只处理用户明确点名的目录/清单。
2. **判定完必须重跑 `extract <批次名>`** —— 判定值在 extract 时写进产物，
   只跑 `merge` 等于没回填。
3. **改动前先快照，改完对三层** —— 快照 + sha256；三层（合并 / 桶层 / 主题层）条数必须对得上。

## 1. 内容侧：加一批新法规

```bash
cd ~/ng-platform

# 1) 写批次清单（绝对路径，一行一个）
#    ~/ng-regs/.batches/<批次名>.list
#    ⚠ 先与本库已有清单做 basename 重叠检查，跨批同名副本会让合并层出现两遍

# 2) 抽取 + 切块
scripts/semantic_build.sh extract <批次名>
scripts/semantic_build.sh chunk

# 3) 判定：把 .classify/chunks/chunk-N.jsonl 分给子代理，产出 class-*.json
#    判定词表：20 税种 × 18 规则；taxes=[] 时 rules 无效（只进事件层）
#    判完抽查：taxes 是否全在词表内

# 4) 收判定并**回填**
scripts/semantic_build.sh collect
scripts/semantic_build.sh extract <批次名>     # ← 关键，不能省

# 5) 分组 → 应用 → 主题层
scripts/semantic_build.sh regroup
#    看 .classify/*.task.json，逐个写 <bucket>.result.json
#    ⚠ apply 的 group 下标 = task['groups'] 里的 0 基下标
.venv/bin/python scripts/reg_semantic_apply.py ...   # 按脚本用法
.venv/bin/python scripts/reg_semantic_topic.py apply

# 6) 三层核对 + 记忆 + 快照
```

### 修订既有法规（最容易踩的坑）

条文 id = `sha8_index`，**条款序列一变，旧 id 全部错位**。修订一份已入库的法规时：

1. 按**文档名精确集合**从 `all-class.json` 删掉该文档的全部旧 id；
2. 重新抽取、重新判定该文档；
3. 重跑 `extract <涉及批次>`，再 regroup / topic apply；
4. 核对该文档在新三层里的条数，不能只看全库总数（分类回填后总数可能下降，
   属分区扇出/去重效应，不是丢条）。

## 2. 交付侧：把封版库打成 `knowledge_regs` 补丁

**包格式 v2（2026-10-21 起）——按源文件分片，只更新受影响的部分。**
每个分片 = 一份 `.md` 的全部条目；改了多少份源文件，增量包就只有多少个分片。
案例库同理（`--kind cases`：一份案例 = 一个分片）。

```bash
cd ~/ng-platform

# 1) 导出交付版（只读封版库，不改内容）
.venv/bin/python scripts/reg_export.py \
    --src ~/ng-regs/_合并_语义/按税种 \
    --out .build/regs-stage

# 2) 建索引 + 分片（按「文档组 + 条文」切块，float16；分片落在 index/shards/）
#    跨文件同一句条文不在建索引时去重（否则另一文件变化时那条会凭空消失），
#    由客户端 load_index 合并时按正文去重。
#    **只算新条文**：已有索引里的向量按正文复用，加一批新法规模块只要几秒；
#    换嵌入模型时加 --no-cache 全量重算。
.venv/bin/python scripts/kb_build_index.py \
    --kb-dir .build/regs-stage --kind regs

# 3a) 完整包（首次发布 / 客户端错过多个版本时的兜底）——必须在增量包之前打
.venv/bin/python scripts/build_kbpack.py --kind regs \
    --src .build/regs-stage --version regs-YYYY-MM-DD \
    --out ~/Desktop/ng-pack --manifest ~/Desktop/ng-pack/update.json \
    --url-base https://github.com/sunxx930/ng-platform/releases/download/v<版本>

# 3b) 增量包（只含与上一版相比变了的分片 + 删除清单）
.venv/bin/python scripts/build_kbpack.py --kind regs \
    --src .build/regs-stage --version regs-YYYY-MM-DD \
    --base ~/Desktop/ng-pack/kb-regs-<上一版>.pack \
    --out ~/Desktop/ng-pack --manifest ~/Desktop/ng-pack/update.json \
    --url-base https://github.com/sunxx930/ng-platform/releases/download/v<版本>
```

产物：`kb-regs-YYYY-MM-DD.pack`（完整）+ `kb-regs-YYYY-MM-DD-delta.pack`（增量），
都已用 `~/.secrets/ng-license/pack.key` 加密。两个 pack 都传到 Release 资产，
`update.json` 发到官网。

manifest 的增量段长这样（`url/sha256/size` 指增量包）：

```json
"knowledge_regs": {
  "version": "regs-2026-11-02",
  "url": "…/kb-regs-2026-11-02-delta.pack", "sha256": "…", "size": 812345,
  "base": "regs-2026-10-21",
  "full": {"url": "…/kb-regs-2026-11-02.pack", "sha256": "…", "size": 38793745}
}
```

客户端选包：`.installed_regs == base` → 下增量；否则（首装/错过版本/内容目录残缺）→
下完整包。增量装完分片数 ≠ `total_after` 会自动用完整包重建一次。

**案例库同理**（一份案例 = 一个分片，manifest 段是 `knowledge`）：

```bash
# 先把案例拷到暂存目录再建索引，别动正在用的 NG_HOME/knowledge
mkdir -p .build/cases-stage && cp -R ~/.ng-platform/knowledge/tax-cases .build/cases-stage/
.venv/bin/python scripts/kb_build_index.py --kb-dir .build/cases-stage --kind cases
.venv/bin/python scripts/build_kbpack.py --kind cases --src .build/cases-stage \
    --version case-YYYY-MM --out ~/Desktop/ng-pack --manifest ~/Desktop/ng-pack/update.json
# 增量：加 --base <上一版 case 完整包>
```

案例完整包带 `models/`（embed + rerank），增量包不带——客户装过完整包就有模型。

### 客户端如何生效

- `update.json` 出现 `knowledge_regs` ⇒ 客户端认为「法规库已上线」，落 `.regs_required`；
- 点「启用税务库 / 检查更新」→ `POST /tax/enable` → 下载（增量或完整）→ sha256 校验
  → 内存解密 → 只重写包内带的分片 `content/shards/<id>.enc`（**永不落明文**）
  → 落 `.installed_regs`；
- 案例库闸门：`knowledge_regs` 存在而法规库未装 → 案例库不可用（堵试用期）；
- 装法规库这一刻 `note_use()` 起算 30 天试用。

### 更新版本号约定

- 版本号就是包文件名/`.installed_regs` 标记值，**变了客户端才会装**；
- 每次发版用 `regs-YYYY-MM-DD`（同日多次加后缀 `-2`）；
- 回滚：把 manifest 的 `knowledge_regs.version` 改回旧版本号并指向旧包，
  客户端发现与 `.installed_regs` 不同就会重新下载安装；
  内容侧回滚用封版/批次快照 `tgz` 恢复后重新打包。

## 3. 收费模式（内置在 App）

| 项 | 口径 |
|---|---|
| App 本身 | 免费 |
| 税务知识库 | **按天计费 1 元/天**：买 N 天转 N 元，授权串有效期 = N 天（`app/services/billing.py` 的 `PLANS` 或 `NG_HOME/billing.json` 可改价） |
| 试用 | 30 天，从**法规库启用**起算（不是装 App 起算） |
| 收款 | **私人收款码**（`data/pay_qr.png`，随安装包分发，不走内容热更） |
| 开通 | 客户扫码转账 → 发机器码 → 发行方 `scripts/issue_license.py` 签发授权串 → 客户在「税务版」面板粘贴激活 |
| 更新权限 | 授权/试用有效才能解密新补丁；到期后 `pack_key()` 返回 None，税务库锁定 |

⚠ **`~/.secrets/ng-license/pack.key` 不要轮换**：老客户的授权串里带着签发当时的 `pk`，
换钥匙会让存量授权解不开新发的知识包。试用密钥 `data/trial_pack.key` 必须与它同值。

签发示例：

```bash
# 按天收费：客户转 N 元（N 天），授权有效期就签 N 天
.venv/bin/python scripts/issue_license.py --mid <机器码> --days 30 --name "客户名"
# 续费时按新增天数再签一段（可用 --exp 直接指定到期日）
.venv/bin/python scripts/issue_license.py --mid <机器码> --exp 2027-03-31 --name "客户名"
```

## 4. 每次更新的检查清单

- [ ] 批次清单与既有清单无 basename 重叠
- [ ] 判定键集 == chunk id 并集；taxes 全在 20 词表内
- [ ] 判定后已重跑 `extract <批次名>`
- [ ] 三层条数一致：`_合并`（税种规则 + 事件）/ 桶层 / 主题层
- [ ] `reg_export.py` 条文行数进出相等
- [ ] `kb_build_index.py --kind regs --check` 无泄漏字段；`index/shards/` 分片数 == 源文件数
- [ ] **先完整包、后增量包**（`--base` 指上一版完整包），两个 pack 都已上传
- [ ] 上一版完整包留档（下一版增量包要拿它当 `--base`；丢了就只能发完整包）
- [ ] 增量包体积远小于完整包；`分片 k/N` 与本次真正改动的文件数相符
- [ ] pack sha256/大小已写入 manifest；pack 已上传到 url 指向位置
- [ ] 改动前快照 + 改动后快照与 sha256 已记录
- [ ] 记忆文件追加本次批次结论（条数、涉税条数、坑）
